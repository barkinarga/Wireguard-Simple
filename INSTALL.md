# Install WireGuard Simple

[README](README.md)

These steps are for your **Debian, Ubuntu, RHEL, CentOS Stream, AlmaLinux, Rocky Linux, or Fedora server**, with systemd and a WireGuard-capable kernel, on amd64 or arm64. The installer refuses Windows and WSL. Your personal computer only needs SSH and a browser to access the panel. See the [distribution requirements](docs/platforms.md), especially for EL8 and immutable Fedora images.

## 1. Download and install

Use this same command for both first installation and future updates. Run on the server:

```bash
curl -fL --retry 3 -o wgsimple-install.run https://github.com/barkinarga/Wireguard-Simple/releases/latest/download/wgsimple-install.run && sudo bash wgsimple-install.run
```

If `curl` is missing, install it first on Debian/Ubuntu:

```bash
sudo apt-get update && sudo apt-get install -y curl ca-certificates
```

On the RPM-based distributions, use `sudo dnf install -y curl ca-certificates` (or `yum` on an EL system without `dnf`). If the server already provides `curl`, including `curl-minimal`, keep that provider. You can also transfer the installer file from your computer.

Alternatively, download `wgsimple-install.run` from the [latest release](https://github.com/barkinarga/Wireguard-Simple/releases/latest), copy it to the server, and run `sudo bash wgsimple-install.run` there. To install without downloading missing system packages, provide those packages yourself and use `--no-deps`.

The installer chooses the architecture, verifies the embedded payload's checksum, installs missing WireGuard tools, IP tools (`iproute2` or `iproute`), `curl`, `kmod`, `nftables`, and `procps`/`procps-ng` (for `sysctl`), then checks kernel support and starts `wgsimple.service`. It uses your enabled repositories; if a package is unavailable, it stops with an explanation. It adds no external repository, kernel, Go compiler, Node.js, Docker, or database service. Temporary extraction files are cleaned up.

Traffic history, persistent administrative logs, and Prometheus are **off on a fresh installation**. Existing settings and client keys are preserved on upgrade. If startup fails, the installer attempts to restore the previous application and service state.

## 2. Open the panel

On your own computer, replace `user@server` with your SSH login and keep this connection open:

```bash
ssh -L 8787:127.0.0.1:8787 user@server
```

On a fresh installation, open **https://127.0.0.1:8787**, including through this SSH tunnel. If that local port is already used by a demo or another program, use `ssh -L 8788:127.0.0.1:8787 user@server` and open **https://127.0.0.1:8788** instead. A preserved loopback-only HTTP service still uses an `http://` address.

The installer displays the first-run token on the **Setup token:** line. Copy it directly into the panel; no editor or command is needed. Treat terminal output containing the token as private. If you need to retrieve it again on the server before setup is complete:

```bash
sudo cat /var/lib/wgsimple/setup-token
```

Enter it in the setup screen and create your administrator account. Keep the token private. Its file is removed after setup; future logins use your username and password. The interface defaults to English; a language selector is available before sign-in and in the top bar, with 10 embedded languages.

On a fresh installation, the panel listens on `0.0.0.0:8787` using **HTTPS**. Open the detected `https://SERVER_IP:8787` address directly if TCP 8787 is allowed by the host/provider firewall. Detection uses an address assigned to the server; behind NAT, use the mapped public address. No external IP lookup service is called. The installer attempts local IPv4 port permissions through an active supported UFW or firewalld. Provider firewall rules remain manual.

Without a custom TLS certificate, the application creates `/var/lib/wgsimple/panel-tls.pem` (or `<data-dir>/panel-tls.pem`), a single private `0600` file containing a server-specific self-signed certificate and private key. The same identity is reused across restarts/upgrades. Version 0.4.3 automatically replaces the Ed25519 identity generated by v0.4.2 with browser-compatible ECDSA P-256; this one-time migration changes the certificate fingerprint. Explicit custom certificates are never replaced. Do not share or publish this file. It is valid for ten years; invalid, expired, symlinked or permissively readable automatic identities stop startup rather than falling back to HTTP. To deliberately replace it, stop the service, preserve the old file privately if needed, remove it, restart, and verify the new fingerprint.

**A browser certificate warning is expected.** Most browsers allow an exception, although browser/device policy may forbid it. Verify the certificate's SHA-256 fingerprint using your trusted SSH connection before accepting:

```bash
sudo openssl x509 -in /var/lib/wgsimple/panel-tls.pem -noout -fingerprint -sha256
```

Self-signed HTTPS encrypts traffic, but blindly accepting any warning does not authenticate the server against an active intermediary. A trusted custom certificate or explicitly trusting the verified self-signed identity avoids that uncertainty. No Cloudflare, domain name or certificate service is needed for direct IP access. Interface addresses, loopback and the initial configured HTTPS origin are included in the generated certificate; accessing a different/NAT address may also produce a name warning. Browser policy can require trusting the certificate explicitly.

Only a **loopback-bound** service may remain plaintext HTTP. A public TLS listener also uses HTTPS when reached via loopback or an SSH tunnel; it does not serve both protocols on the same port.

## 3. Prepare VPN connectivity

An empty **Settings → Endpoint** is filled automatically when exactly one public IPv4 address is assigned to the server outside the managed VPN interface. Saved endpoints are preserved. NAT-only hosts, multiple public IPv4 addresses or detection failures require a manual public IP/domain; no external IP lookup service is contacted.

New installations take client DNS defaults from the server's IPv4 resolvers. Local stubs such as `127.0.0.53` are skipped; the application checks systemd-resolved's upstream configuration when needed. It never substitutes a fixed DNS provider. If no usable IPv4 resolver can be detected, enter one manually or leave DNS empty to keep device DNS. Detection cannot guarantee that a provider's private DNS is reachable by every client. Existing saved DNS settings are preserved; **Use server DNS** fills the Settings DNS field from the current host configuration, then **Apply server settings** saves it.

Use **Add client** to create a device and obtain its configuration or QR code. The optional **Advanced settings** section expands the dialog: choose an available VPN `/32`, DNS mode/custom DNS, AllowedIPs, endpoint/UDP port, MTU, keepalive, client listen port, FwMark, private key and preshared key. Empty fields inherit defaults or generate keys. Keepalive `0` disables it; listen port `0` selects automatically. Existing clients continue to inherit the server values unless they have explicit overrides. DNS can also be omitted to keep the device's own DNS. Exported routing settings configure the client, not server-side access restrictions. Server-owned interface settings and the server public key stay managed by the panel.

**Fresh installations prepare the IPv4 VPN interface, forwarding and NAT automatically.** A dedicated `wgsimple-network.service` runs before the panel and restores networking on boot. NAT is limited to traffic arriving on the saved WireGuard interface from its saved subnet and leaving the detected default IPv4 uplink. Rules are replaced atomically in an application-owned nftables table; other tables are not flushed. DNS settings and the system default route are preserved.

Active UFW or firewalld is detected and configured through its own CLI. IPv4 input permissions cover the actual panel TCP port (unless bound to loopback) and saved VPN UDP port on the selected uplink. VPN forwarding is limited to the managed interface/subnet and that uplink; NAT remains in the application-owned nftables table. Firewall enablement, SSH rules and default policies are preserved. Repeated setup does not add duplicate permissions. Failures roll back additions made during the failed firewall operation.

For firewalld, a dedicated VPN zone and egress policy avoid trusting the VPN with unrestricted host access or enabling global masquerade. The first setup needs a reload: it proceeds only if the inspected runtime and permanent state agree. Real runtime-only rule changes, custom/source-based zones, conflicting managers, legacy iptables, mixed/custom filter chains, explicit UFW deny/reject/limit rules and ambiguous uplinks require administrator-managed setup. Port preparation failures print a manual warning; managed-network failures stop before claiming that VPN networking is ready.

Use `--no-network` to skip all automatic firewall/VPN networking changes, or `--no-start` to install files only. Configure forwarding, NAT, port access and boot startup manually in those cases. Automatic permissions cannot prove that the panel or VPN is reachable through every upstream firewall.

Allow the saved WireGuard UDP port in your provider firewall (default **51820/UDP**). Provider firewall rules and public/NAT endpoint detection are outside local automatic setup. After changing the subnet or uplink on a managed installation, rerun with `--configure-network` to refresh NAT. Existing managed firewalld objects with a different subnet/zone must first be reconciled manually; old permissions are not silently broadened or deleted.

Live management actions can create or update the selected WireGuard interface. For an existing VPN, import its matching server configuration before managing clients. Server files do not contain client private keys, so imported clients cannot receive regenerated client configurations from that import alone.

Ubuntu 26.04.1 ARM64 KVM startup, a real WireGuard handshake, and a tunnel ping with a temporary client namespace on the same host have been verified. Internet ping, DNS and HTTPS have also passed through a temporary VPN client namespace. External-device connectivity and full-machine reboot recovery have not yet completed end-to-end validation for this early release. Test on a dedicated Linux server before relying on it.

## Update

Run the same command from step 1 whenever you want to update. No uninstall or manual file replacement is needed.

From v0.4.1, an installer you previously downloaded also checks GitHub each time you run `sudo bash wgsimple-install.run`. If a newer stable release exists, it downloads that release and its checksum from the same pinned tag, verifies the package, then installs it. If the installed version is already current or newer, a default run reports that and exits without restarting services. Explicit options such as `--configure-network` still run.

A failed GitHub check, download or checksum stops before installation and leaves the running application untouched. `--check` does not perform a release lookup. For an intentional offline/pinned-package installation, use `--no-update-check` (plus `--no-deps` if package downloads are also unwanted); this uses the embedded version and does not promise the newest release. Installers downloaded before v0.4.1 gain this behavior only after downloading the new installer once.

During an actual update the panel briefly restarts; existing clients, administrator credentials, service configuration and recording preferences are preserved. Existing networking is refreshed only under the established managed-network behavior. The updater adds no background scheduler and no persistent update downloads. You can delete the downloaded `.run` file after installation.

## Useful commands

| Task | Command |
| --- | --- |
| Check the environment without installing | `bash wgsimple-install.run --check` |
| Install files without starting the panel | `sudo bash wgsimple-install.run --no-start` |
| Use administrator-managed VPN networking | `sudo bash wgsimple-install.run --no-network` |
| Prepare networking on an existing installation | `sudo bash wgsimple-install.run --configure-network` |
| Use the embedded version without a GitHub release check | `sudo bash wgsimple-install.run --no-update-check` |
| Skip automatic system package installation | `sudo bash wgsimple-install.run --no-deps` |
| Choose an interface on a fresh installation | `sudo bash wgsimple-install.run --interface wg1` |
| Check the panel service | `sudo systemctl status wgsimple.service` |
| Restart the panel | `sudo systemctl restart wgsimple.service` |
| Stop the panel | `sudo systemctl stop wgsimple.service` |

An upgrade preserves the interface and existing service file. Non-loopback listeners automatically migrate to HTTPS, including units containing the deprecated `--allow-http` flag; change bookmarks to `https://`. An explicit public `--origin http://...` must be changed to HTTPS before starting the new binary. Existing custom TLS certificates are preserved. With custom origin restrictions, the installer's loopback health check may not apply; install using `--no-start` and start the service with your own configuration. The readiness check skips certificate verification only for its credential-free loopback HTTPS probe; release downloads still verify HTTPS normally.

Stopping the panel leaves an existing WireGuard interface running, but disables monitoring and client expiry enforcement until the panel runs again. Fresh installations use the dedicated network bootstrap at boot. Existing installations keep their previous startup policy; use `--configure-network` to opt into managed IPv4 networking.

## Panel access and recovery

In **Settings → Panel access**, choose **Public access**, **This server only**, or **Private networks only**. Optionally add up to 64 IP addresses or CIDRs, separated by commas or newlines. The allowlist intersects with the selected mode. Loopback is always admitted. Private networks mean RFC1918 IPv4 and unique-local IPv6 source addresses, including VPN networks; this is not a location check.

The policy takes effect on every new request, including sign-in, static files, metrics, and health checks. It is stored in `/var/lib/wgsimple/panel-access.json` with private permissions and persists through restart/upgrade. Blocking sources returns HTTP 403; it does not close the listening socket or change firewall rules. Source IP comes from the TCP connection; forwarded headers are ignored. A local reverse proxy therefore appears as loopback: enforce source restrictions in the proxy itself.

If you lock yourself out, run over SSH:

```bash
sudo systemctl stop wgsimple.service
sudo /usr/local/bin/wgsimple --mode live --data-dir /var/lib/wgsimple --reset-panel-access public
sudo systemctl start wgsimple.service
```

Use `local` instead of `public` to recover to loopback-only admission, or `lan` for private networks. This clears the allowlist without changing accounts, passwords, VPN keys, or history. Alternatively, while stopped, edit `panel-access.json` to `{"mode":"public","allowlist":[]}` and restart. Invalid files prevent startup rather than silently exposing the panel.

### Upgrading a previous loopback-only installation

Upgrades preserve the existing service listener. If it still uses `--listen 127.0.0.1:8787`, the panel policy cannot make that socket public. Run `sudo systemctl edit --full wgsimple.service` and replace only `--listen 127.0.0.1:8787` with `--listen 0.0.0.0:8787` in `ExecStart`, preserving all other arguments. HTTPS is enabled automatically with the private self-signed identity. Then run:

```bash
sudo systemctl daemon-reload
sudo systemctl restart wgsimple.service
```

To use a trusted custom certificate instead of the automatic self-signed certificate, supply `--tls-cert`, `--tls-key`, and an explicit HTTPS `--origin`. That canonical origin controls which address the browser must use. A hostname URL requires the matching `--origin`; direct IP access works without one. `--allow-http` is accepted only for old service-file compatibility and can no longer enable public HTTP. Invalid custom certificates/keys prevent startup without replacing them or falling back to plaintext.

## Ubuntu 26 startup compatibility

Version 0.3.2 starts a new managed interface using direct `ip` and `wg` commands. This avoids a reproduced conflict between the distribution wg-quick AppArmor child-profile transitions and NoNewPrivileges. AppArmor and the service restrictions remain enabled. Existing interfaces still use `wg syncconf` for updates. The generated wg-quick-compatible configuration is retained for external startup after reboot. Fresh interfaces with client subnets outside the server VPN network require external setup and import; the panel does not silently omit their routes.

## Minimal server prerequisites

The executable installer checks dependencies before its first extraction or release download. On a normal run it installs missing core utilities, grep/awk/sed, tar+gzip (or uses an existing bsdtar), curl and CA certificates, systemctl, WireGuard tools and the applicable IPv4 network tools. Existing callable curl providers, including curl-minimal, are preserved. Package setup uses only enabled distribution repositories and retries a failed transaction once after a metadata refresh. It verifies required commands and the CA bundle before touching application services or data.

If repositories, connectivity or subscription access cannot provide the packages, setup stops with an actionable error. It never adds unrequested repositories, bypasses package/TLS verification, skips checksum checks or executes a partially unpacked payload. `--no-deps` refuses missing prerequisites; `--check` lists them without installing. If tools needed to inspect/unpack the package itself are missing during `--check`, it stops after reporting them. The outer download command still requires curl/sudo to already be usable, or you can transfer the installer file over SSH and run it as root.

CentOS Stream 10 is covered by an executable-header regression test that starts without tar. Container checks exercise dependency setup and package extraction, not a complete booted VM or every provider image. WireGuard-capable kernel and running systemd requirements remain unchanged.

A runtime-only NetworkManager binding of the actual uplink to firewalld's default zone is accepted when the permanent configuration leaves that interface unbound; both have the same effective zone. This exception does not ignore port/service/rule differences or assignments to other zones. Managed network setup writes a private `network-managed` intent marker in the data directory so a normal retry can resume after a failed fresh installation. Failed installations from older versions without that marker may need one explicit `--configure-network` retry.
